## Prioridad exacta de práctica para el assessment

### Sí entrenar

1. Listas y strings: recorrer, índices, `len`, slicing, `split`, `strip`, `lower`, y sorting.
2. Diccionarios: frecuencias, valor → índice, acumulación y consultas con `in` / `get`.
3. Sets: detectar repetidos y membership rápido.
4. Loops, condiciones y funciones limpias que devuelven el tipo pedido.
5. Casos borde: vacío, un elemento, duplicados, negativos, índices límite, mayúsculas/minúsculas cuando aplique.
6. Stack simple con lista (`append` / `pop`) y simulaciones simples de estado.
7. Ordenar + dos punteros, solo después de consolidar los puntos anteriores.

### No priorizar ahora

- Regex, fechas, HTTP/APIs, web scraping, Playwright, archivos, clases/OOP, decoradores y Python avanzado.
- Árboles, grafos, recursión y programación dinámica: solo si sobra tiempo tras dominar lo anterior.

## Reglas de práctica conmigo

- Ping-pong: primero explicar el enunciado de forma simple; Fausto intenta; después revisar razonamiento, código y tests.
- No dar solución de entrada.
- Los ejercicios nuevos irán dentro de `ejercicios_practicos/`; la carpeta queda vacía hasta empezar a crear uno.
- El material de aprendizaje existente está dentro de `clases/`.
- Antes de entregar cualquier solución, probar explícitamente: entrada vacía, mínimo tamaño válido, duplicados, negativos si aplican y límite de índices.

## Checklist para el día del assessment

- Usar computadora de escritorio/notebook, conexión estable y navegador actualizado.
- Desactivar extensiones que puedan interferir o abrir una ventana incógnita. CoderPad lo recomienda para Screens.
- Empezar solo cuando haya 90 minutos sin interrupciones: al iniciar corre el reloj.
- Leer primero el contrato de la función: nombre, parámetros y retorno. No usar `input()`, `print()` ni `os.system()` salvo que el enunciado lo exija.
- Resolver primero los ejemplos, luego agregar tests propios de borde antes de enviar.
- Usar Google/Stack Overflow solo para sintaxis específica y nunca para buscar la solución del ejercicio.
- CoderPad conserva reproducción de la actividad de código para los evaluadores; escribir de manera incremental, clara y propia.

### Controles de actividad y prevención de trampas

La documentación de CoderPad distingue entre **Interview** (sesión en vivo) y
**Screen** (assessment asíncrono). La invitación de ElevenLabs es para Screen,
por lo que no hay que asumir que cada control de Interview se aplica idénticamente.

Para Interview en vivo, CoderPad documenta que puede registrar una línea de tiempo
con ediciones, ejecuciones, movimientos de cursor, copy/paste y salidas de la IDE;
también puede alertar al entrevistador si se pega código externo o se sale de la
IDE. Las alertas son señales para pedir contexto, no una descalificación automática.
La guía no afirma que haya grabación de toda la pantalla por defecto; en entrevistas
de alta seguridad un entrevistador puede pedir screen sharing.

Para Screen, CoderPad documenta playback de actividad de programación: escritura,
ejecuciones/envíos, pegados y salidas/regresos al test. La configuración concreta
depende del assessment de ElevenLabs.

Implicación práctica:

- Usar Google o Stack Overflow para una duda puntual de sintaxis está autorizado
  por el correo de ElevenLabs. Una salida breve al navegador no equivale por sí
  misma a una penalización automática.
- No usar IA ni buscar/copiar la solución del ejercicio.
- No resolver el ejercicio completo en otro editor y pegar bloques grandes en
  CoderPad, incluso si fueran propios: el código debe desarrollarse directamente
  en la evaluación.

Fuentes: [prevención de trampas en Interview](https://coderpad.io/resources/docs/cheating-prevention-in-interview/) y [playback de Screen](https://coderpad.io/resources/docs/screen/candidate-reports/code-playback/).

[Guardrails](https://elevenlabs.io/blog/guardrails) · [monitoreo](https://elevenlabs.io/docs/eleven-agents/guides/realtime-monitoring)
- El enfoque de mejora es continuo: evaluar conversaciones, detectar fallas y cambiar/validar configuración antes de publicar. [Spotlight](https://elevenlabs.io/blog/introducing-elevenagents-spotlight) · [testing de agentes](https://elevenlabs.io/blog/testing-conversational-ai-agents)
- Una lección explícita de su equipo de Forward Deployed Engineering: optimizar resolución real, no solamente “deflection”; para eso el agente necesita contexto, acceso a los sistemas que ejecutan acciones y handoff humano con contexto. [Building voice agents that last](https://elevenlabs.io/blog/building-voice-agents-that-last-some-lessons-learned-from-forward-deployed-engineering)

Cuando termine el assessment, esto se convierte en práctica de entrevistas: explicar Paloma con problema → discovery → arquitectura → implementación/integraciones → handoff → métricas → iteración.
